# Manage Iteration

## Purpose

Centralize every iteration-number operation. The iteration identifier format is `v{major}.{minor}`; see AGENTS.md §17 for the full versioning rules.

1. **Detect the next iteration number**: scan the existing `v{N}(.{M})?/` directories under `iteration/`, and return `v{N+1}.0` (major bump) or `v{N}.{M+1}` (minor bump).
2. **Create a new iteration skeleton**: create the five empty delivery-stage subdirectories under `iteration/v{N}/`; raw user requirements are stored centrally under `iteration/raw-requirement/`.
3. **Archive a finished iteration**: after the next consecutive version's skeleton is created successfully and the instance root `README.md` has merged the RC-complete predecessor's functionality into the current system-functionality section, move the predecessor wholesale to `iteration/archive/v{N}/` and record the archive time.
4. **Resolve the active iteration**: return the latest Approved iteration number for use by other skills.

## Path Conventions

```text
Project Root
├── iteration/
│   ├── v1/                                  ← currently active
│   ├── v2/                                  ← currently active
│   └── archive/
│       └── v1/                              ← RC-complete snapshot
```

## Operations

### 0. Initialize Project and Version

```powershell
python .workflow/workflow.py init
python .workflow/workflow.py init-version
```

`init` creates `baseline/raw-requirement/`, `iteration/raw-requirement/`, `iteration/`, and `workspace/`, and writes the workflow-entry explanatory files. `workspace/README.md` is created and maintained by the instance project itself: it only explains how the workspace works and is not generated by the workflow to carry current-version functionality. The instance root `README.md` is instance-owned; after `05-review-release` passes, the workflow refreshes its current-system-functionality section from the release log. `iteration/raw-requirement/README.md` is the only explanatory file in that directory; everything else in it is raw user material. `init` applies to projects that have not yet started and does not create any version directory.

`init-version` may create the next consecutive version's directory skeleton only after `validate --stage 00-baseline` passes, and refreshes the manifest automatically. The first version is `v1.0`; it creates only the five formal stage directories and creates or approves no artifacts. Before any later version is created, the active predecessor must pass `validate --stage 05-review-release`, and the instance root `README.md` must complete the current-system-functionality refresh. After the new skeleton is created, the CLI archives the predecessor automatically; if the refresh check fails, the predecessor and the new skeleton both remain unchanged.

### 1. Detect Next Version

Scan the `v{N}(.{M})?/` directory names under `iteration/` and return the next iteration number.

```python
import re
from pathlib import Path

def next_version(iteration_dir: Path) -> str:
    """Return the next iteration id given existing v{major}.{minor} directories.

    Bumps the minor when current major matches the highest seen; otherwise
    starts a new major at `.0`.
    """
    pattern = re.compile(r"v(\d+)(?:\.(\d+))?$")
    pairs: list[tuple[int, int]] = []
    for p in iteration_dir.iterdir():
        if not p.is_dir():
            continue
        m = pattern.match(p.name)
        if m:
            pairs.append((int(m.group(1)), int(m.group(2) or 0)))
    if not pairs:
        return "v1.0"
    pairs.sort()
    major, minor = pairs[-1]
    # Decision rule: bump minor by 1. Promote to (major+1, 0) only when the
    # caller explicitly signals a baseline shift; default behavior stays in-major.
    return f"v{major}.{minor + 1}"
```

`next_version` MUST NOT return `v1.0` when `stage-gate` has not passed for `00-baseline`; the baseline review must succeed first.

### 2. Create New Version Skeleton

```text
iteration/v{N}/
├── 01-product/
├── 02-design/
├── 03-planning/
├── 04-implementation/
└── 05-review-release/
```

Create empty directories only; place no files inside. Raw user requirements are stored centrally in `iteration/raw-requirement/` in their original format and original wording; that directory is the input for `normalize-requirement` and does not require `status: Approved`. Run `route-requirement` first to obtain its target version; the raw files are read-only, and agents MUST NOT modify, rename, or delete them.

### 3. Archive Previous Version

Trigger: after the next consecutive version's skeleton has been created successfully. The predecessor being archived MUST have already passed `validate --stage 05-review-release`; its release artifact records the review, merge, release decision, and release notes.

Execution steps:

1. Create the next consecutive version's five stage directories; if this step fails, do not archive.
2. Create the `iteration/archive/v{N}/` directory (where `{N}` is the predecessor's iteration number, such as `v1.0` or `v1.1`).
3. Move **all content** under `iteration/v{N}/` into `iteration/archive/v{N}/`.
4. Write the archive metadata into `iteration/archive/v{N}/ARCHIVED.md`:

```text
# Archive: v{N}

- archived_at: YYYY-MM-DD
- superseded_by: v{next_major}.{next_minor}
- rc_artifact: iteration/v{N}/05-review-release/v{N}-review-release.md
- release_log: iteration/v{N}/05-review-release/v{N}-release-log.md  (reference)
- note: this directory is read-only; do not modify.
```

5. Do not delete the archived version's release log; the archive directory is a read-only snapshot.

#### Instance README refresh

Before the predecessor is archived, the new functionality of that version MUST be merged into the instance root `README.md` under the current-system-functionality section and the precise marker MUST be added or updated:

```html
<!-- workflow:current-system-functionality-version: v{major}.{minor} -->
```

The CLI only validates the file, the marker, and the heading; it does not invent business functionality. The `05-review-release` gate updates the marked root README section from the release log; `init-version` runs that check before archiving; any failure blocks the archive.

### 4. Resolve Current Active Version

Return the latest **Approved** iteration number:

1. Read the frontmatter `status` of every `iteration/v{major}.{minor}/05-review-release/v{major}.{minor}-review-release.md` under `iteration/`.
2. Sort descending by `(major, minor)` and find the first iteration with `status: Approved`.
3. If none is Approved, return the iteration with the largest `(major, minor)` (even if still draft).

## Failure Handling

- **Iteration numbers may not be skipped** (for example, forbid going from v1.0 directly to v1.2; majors may not be skipped from v1 to v3).
- **Archived iterations under `iteration/archive/` may not be overwritten.**
- **`iteration/v1.0/` may not be created** without passing the `stage-gate` `00-baseline` gate. A subsequent upgrade MUST stop when the predecessor's `05` gate has not passed, and the predecessor may not be moved.
- When a conflict is detected (for example, a `v{major}.{minor}/` directory was created manually without going through this skill), report it and request a human decision.

## Common Mistakes

| Mistake | Correction |
|---|---|
| Directly `mkdir iteration/v1.1/` without invoking this skill | Use manage-iteration so the references and archive chain stay complete. |
| Archive the predecessor but forget to write the release log | Prompt the user: `v{major}.{minor}-release-log.md` must exist (it is required to exist before `05-review-release` passes; no extra write is needed before archive). |
| Manually edit files under `iteration/archive/v{N}/` | Block; if a correction is needed, open a new iteration. |
Instance documentation ownership: `AGENTS.md` and root `README.md` are created during initialization and then remain instance-owned; `sync` updates only `.aw/README.md` and other workflow files. The root README's marked current-system-functionality section is refreshed after 05-review-release, while `workspace/README.md` remains static workspace guidance.

This ownership rule supersedes any earlier wording in this skill that describes the root README as framework-owned.
